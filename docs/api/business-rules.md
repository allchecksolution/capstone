## BR-01 상태 구분과 전이

요구사항의 업무 흐름에서 서로 독립적으로 관리할 필요가 있는 상태를 구분하여 아래 12개 대상을 선정했다. 요구사항이 이 12개 대상이나 개체 구조를 그대로 정의한 것은 아니다. 예를 들어 기사 배정이 해제되어도 고객 의뢰는 유지되고 취소 후속 처리는 관리자 결정을 기다릴 수 있으므로, 이를 하나의 `status`에 합치지 않는 설계를 제안한다. 아래 영문 개체·필드·상태명과 상세 전이는 별도 표시가 없으면 설계 제안이다. 사용자 결정(2026-11-01)은 이번 대화에서 정한 정책이며 기존 requirements 원문과 구분한다.

### 대상별 근거 문서와 내용 / Codex가 설계로 추가한 부분

아래 12개 항목은 현재 requirements 원문과 대조하고 사용자 결정을 반영한 결과다. 각 항목에서 **근거 문서와 내용**은 요구사항에 명시된 업무 조건을, **Codex가 설계로 추가한 부분**은 그 조건을 구현하기 위해 Codex가 제안한 개체·필드·상태·처리 정책을 뜻한다. 출처 문서가 연결되어 있어도 Codex의 설계가 요구사항으로 확정되는 것은 아니다. 개체 분리는 논리 모델 제안이며 DB 테이블 분리를 확정하지 않는다.

#### 1. 관리자 접수 검토 상태 `reception.reviewStatus`

**근거 문서와 내용**

[FR-04](../requirements/functional-requirements/fr-04-ai-analysis-result-review-and-edit.md) 세부 5~7, [UC-02](../requirements/use-cases/uc-02-ai-reception-review.md) 기본 흐름 5~6: 관리자가 검토를 완료하고 최종 접수 정보를 확정·저장한다. 수동 입력도 같은 확정 절차를 따른다. [FR-05](../requirements/functional-requirements/fr-05-request-registration-and-dispatch-candidate-selection.md) 세부 1: 검토 완료된 접수정보를 의뢰로 등록한다.

**기존 내용에 덧붙여서 설계**

검토 여부를 별도 `reviewStatus` 필드와 `DRAFT → CONFIRMED`로 표현한다. AI 처리 상태와 관리자 검토 상태를 별도로 관리한다.

#### 2. 접수 처리 단계 상태 `recordingStatus`, `sttStatus`, `analysisStatus`

**근거 문서와 내용**

[FR-02](../requirements/functional-requirements/fr-02-call-recording-collection-and-stt-transcription.md) 세부 5~6: 녹음 확보·STT 실패를 기록하고 수동 접수를 지원한다. [FR-03](../requirements/functional-requirements/fr-03-ai-consultation-analysis-and-structuring.md) 세부 5: AI 분석 실패를 기록한다. [UC-02](../requirements/use-cases/uc-02-ai-reception-review.md) 기본 흐름 2·예외 E1: 실제 존재하는 자료만 표시하고 처리 실패 시 수동 입력으로 연결한다.

**기존 내용에 덧붙여서 설계**

세 처리 단계를 각각의 상태 필드로 분리하고 `PENDING/PROCESSING/SUCCEEDED/FAILED/NOT_AVAILABLE`를 사용한다. **사용자 결정(2026-11-01):** `PENDING`은 실행 대기, `PROCESSING`은 처리 중이다. 정상 처리 흐름은 `PENDING → PROCESSING → SUCCEEDED`이며 실패 시 `FAILED`로 기록한다. 자료 존재 여부와 실패를 구분하는 구체적인 표현 방식은 설계 제안이다.

#### 3. 의뢰 상태 `request.status`

**근거 문서와 내용**

[UC-03](../requirements/use-cases/uc-03-dispatch-request.md) 기본 흐름 3: 의뢰를 생성한다. [FR-12](../requirements/functional-requirements/fr-12-dispatch-cancellation-and-redispatch-management.md) 세부 3·5~6, [UC-07](../requirements/use-cases/uc-07-dispatch-cancellation-review.md)·[UC-13](../requirements/use-cases/uc-13-dispatch-cancellation-request.md) 사후 조건: 기사 배정 해제와 고객 의뢰 취소는 다르며 관리자가 재배차 또는 의뢰 취소를 결정한다.

**기존 내용에 덧붙여서 설계**

의뢰 자체의 생명주기를 `OPEN/COMPLETED/CANCELLED`로 모델링한다. **사용자 결정(2026-11-01):** 현재 유효한 담당자가 작업을 모두 마치고 최초 보고서를 정상 제출하면 작업을 `WORK_DONE`, 해당 의뢰를 `COMPLETED`로 함께 변경한다. 보고서 작성 화면 진입·미제출·저장 실패만으로 의뢰를 완료하지 않는다. 재방문이 필요한 동안에는 의뢰를 `OPEN`으로 유지하며, 담당자 인계만으로도 완료하지 않는다.

#### 4. 배차 회차 상태 `round.status`

**근거 문서와 내용**

[FR-05](../requirements/functional-requirements/fr-05-request-registration-and-dispatch-candidate-selection.md) 세부 8~9, [UC-03](../requirements/use-cases/uc-03-dispatch-request.md) 기본 흐름 4~6·예외 E2~E4: 후보 탐색·전달 및 실패 결과를 관리한다. [UC-07](../requirements/use-cases/uc-07-dispatch-cancellation-review.md) 기본 흐름 4~5, [FR-16](../requirements/functional-requirements/fr-16-work-history-and-statistics-management.md) 세부 7: 과거 이력을 보존하고 재배차하며 현재 배차와 과거 이력을 구분한다.

**기존 내용에 덧붙여서 설계**

**독립적인 `round` 개체 자체를 설계로 추가했다.** 요구사항은 회차 개체를 지정하지 않는다. 재배차마다 새 회차를 생성하고 각 회차에 탐색·전달·배정 상태를 부여하는 방식과 상태 목록은 제안이다.

**사용자 결정(2026-11-01):** 모든 대상 기사가 거절한 회차는 `NO_ACCEPT`, 수락 없이 유효시간이 만료된 회차는 우선 `ROUND_CLOSED`로 기록한다. 개별 요청의 `REJECTED`/`EXPIRED`와 회차 결과를 구분한다. 거절·만료·전달 실패가 섞인 회차의 종료 분류는 후속 결정한다.

#### 5. 기사별 반응 상태 `offer.status`

**근거 문서와 내용**

[FR-07](../requirements/functional-requirements/fr-07-dispatch-request-delivery-and-notification.md) 세부 1·3·5: 기사별 요청을 생성하고 종료되거나 다른 기사에게 배정된 요청은 무효로 처리한다. [FR-08](../requirements/functional-requirements/fr-08-dispatch-request-acceptance-and-rejection.md) 세부 1·3·6, [UC-10](../requirements/use-cases/uc-10-dispatch-request-response.md) 기본·예외·대안 흐름: 개별 수락·거절, 한 기사만 확정, 다른 요청 종료, 만료를 처리한다.

**기존 내용에 덧붙여서 설계**

기사별 요청을 `offer`로 명명하고 기사별 반응 상태를 `PENDING/ACCEPTED/REJECTED/EXPIRED/RESPONSE_CLOSED`로 표현한다. 대상 기사·회차·만료 시각을 고정하는 모델은 설계 제안이다.

#### 6. 전달 상태 `offer.deliveryStatus`

**근거 문서와 내용**

[UC-03](../requirements/use-cases/uc-03-dispatch-request.md) 기본 흐름 6·예외 E3~E4, [FR-09](../requirements/functional-requirements/fr-09-request-and-work-status-management.md) 세부 8: 전체·일부 전달 실패와 기사별 결과를 관리하고, 푸시 발행·전달 서비스 접수와 실제 수신·확인을 구분한다.

**기존 내용에 덧붙여서 설계**

수락·거절과 독립적인 `deliveryStatus`를 두고 `PENDING/PROVIDER_ACCEPTED/FAILED`를 사용한다. 실제 수신·확인을 `receivedAt`, `viewedAt`으로 기록하고 확인 신호가 없으면 null로 표현하는 방식도 제안이다.

#### 7. 확정 배정 상태 `assignment.status`

**근거 문서와 내용**

[FR-08](../requirements/functional-requirements/fr-08-dispatch-request-acceptance-and-rejection.md) 세부 3: 한 기사만 담당자로 확정한다. [FR-12](../requirements/functional-requirements/fr-12-dispatch-cancellation-and-redispatch-management.md) 세부 3·5·7~8, [UC-13](../requirements/use-cases/uc-13-dispatch-cancellation-request.md): 유효 배정을 확인하고 취소 접수 즉시 해제하며 이력을 보존한다. [FR-16](../requirements/functional-requirements/fr-16-work-history-and-statistics-management.md) 세부 7: 과거 배정과 현재 배차를 구분해 조회한다.

**기존 내용에 덧붙여서 설계**

기사와 의뢰의 연결을 독립 `assignment` 개체와 `POSSIBLE/RELEASED/FINISHED`로 표현한다. 과거 배정을 다시 활성화하지 않고 새 ID로 재배정하는 방식은 제안이다. **사용자 결정(2026-11-01):** 작업 완료 후 배정이 `POSSIBLE`로 남아 있어도 다른 적합한 의뢰를 수락할 수 있다. 배정 유효성과 미완료 작업 점유를 별도로 판단하며, 기사당 `POSSIBLE` 배정 하나라는 제약을 두지 않는다. 보고서 제출만으로 자동 `FINISHED` 처리하던 기존 제안은 제거하고 배정 종료 시점은 후속 결정한다.

#### 8. 작업 상태 `work.status`

**근거 문서와 내용**

[FR-09](../requirements/functional-requirements/fr-09-request-and-work-status-management.md) 세부 3~7, [UC-11](../requirements/use-cases/uc-11-work-status-update.md) 기본 흐름·예외 E2/E4·대안 A1: 유효 담당자가 작업 시작·완료 상태를 변경하고, 허용되지 않은 전이를 거부하며 재방문 상태를 관리한다.

**기존 내용에 덧붙여서 설계**

작업 상태를 배정/작업 단위로 보존한다. **사용자 결정(2026-11-01):** 최초 보고서 제출 성공 시 작업을 `WORK_DONE`으로 변경한다. 같은 담당자가 재방문하면 같은 작업 ID를 유지하고 이동·도착 단계를 다시 거친다. 담당자가 바뀌면 기존 작업은 종료하고 새 작업·배정을 생성한다. 새 담당자는 연결된 이전 작업 기록을 조회할 수 있고, 기존 담당자는 종료된 작업을 새로 변경할 수 없다.

**구현 제안:** 같은 담당자의 재방문은 `REVISIT_REQUIRED → EN_ROUTE → ARRIVED → IN_PROGRESS`로 이어간다. 담당자 변경으로 끝난 기존 작업은 `TRANSFERRED`(인계 종료)로 기록하고 기존 배정은 `FINISHED`로 닫는다. 이 상태명은 보고서 제출로 끝난 `WORK_DONE`과 구분하기 위한 제안이며 완료 건수에 포함하지 않는다. 새 작업은 `NOT_STARTED`에서 시작하고 이전 작업 ID를 연결한다. 인계 시 기존 작업·배정 종료와 새 작업·배정 생성을 함께 처리한다. 이전 기록 조회는 새 담당자의 유효 배정과 관련 의뢰·파일 접근 권한을 확인한다.

#### 9. 취소 후속 처리 상태 `cancellation.resolutionStatus`

**근거 문서와 내용**

[FR-12](../requirements/functional-requirements/fr-12-dispatch-cancellation-and-redispatch-management.md) 세부 3·6, [UC-13](../requirements/use-cases/uc-13-dispatch-cancellation-request.md) 기본 흐름 5~7, [UC-07](../requirements/use-cases/uc-07-dispatch-cancellation-review.md) 기본 흐름 4·대안 A1·사후 조건: 즉시 해제 후 관리자 후속 처리를 기다리고, 재배차 또는 의뢰 취소 중 하나만 결정한다. 취소 처리 상태와 의뢰 상태를 구분한다.

**기존 내용에 덧붙여서 설계**

후속 결정을 별도 `resolutionStatus`와 `PENDING → REDISPATCH/CANCEL_REQUEST`로 표현한다. `REDISPATCH`를 새 배정 완료가 아닌 관리자 결정 완료로 정의하는 것은 상태 모델 제안이다.

#### 10. 기사 작업 가능 여부 상태 `driver.availability`

**근거 문서와 내용**

[FR-10](../requirements/functional-requirements/fr-10-driver-availability-status-management.md) 및 [UC-09](../requirements/use-cases/uc-09-driver-availability-management.md): 기사는 대기 또는 휴식 상태를 설정하고, 대기 상태에서 다른 후보 조건도 만족할 때 신규 배차 후보에 포함된다.

**사용자 결정(2026-11-01)**

상태값은 `READY/VACANT`로 한다. 기존 대기/휴식에 각각 대응하여 `READY`는 작업 가능(대기), `VACANT`는 작업 불가(휴식)로 해석한다. **기사 계정 상태를 우선 확인하고 `APPROVED`인 경우에만 `READY/VACANT`를 배차 판단에 사용한다.** 승인 대기·반려·탈퇴 계정은 저장된 값이 `READY`여도 신규 배차 대상이 아니다. 작업 진행 상태와 별도로 관리하며, `APPROVED + READY`여도 전문 분야·지역·위치·미완료 작업 점유 조건을 확인한다. 완료된 작업의 `POSSIBLE` 배정만으로 신규 수락을 막지 않는다.

#### 11. 기사 계정 상태 `driver.accountStatus`

**근거 문서와 내용**

[FR-13](../requirements/functional-requirements/fr-13-driver-registration-and-authentication.md), [UC-06](../requirements/use-cases/uc-06-driver-registration-approval.md), [UC-08](../requirements/use-cases/uc-08-driver-registration.md), [UC-15](../requirements/use-cases/uc-15-driver-account-withdrawal.md): 사업자 검증 후 승인 대기로 등록하고, 관리자 승인 시 활성, 반려 시 반려, 탈퇴 시 탈퇴 상태로 관리한다. 반려 후 재신청은 기존 계정을 사용하며, 활성 계정만 정상 서비스 이용과 신규 배차 후보 선별 대상이 된다.

**사용자 결정(2026-11-01)**

`PENDING_APPROVAL`(승인 대기) / `APPROVED`(활성) / `REJECTED`(반려) / `WITHDRAWN`(탈퇴)으로 정의한다. 가입 승인 시 `PENDING_APPROVAL → APPROVED`, 반려 시 `PENDING_APPROVAL → REJECTED`, 검증 후 재신청 제출 시 `REJECTED → PENDING_APPROVAL`로 전이한다. 탈퇴 허용 조건을 만족해 정상 처리되면 `WITHDRAWN`으로 변경한다. 계정의 `APPROVED`와 배정의 `POSSIBLE`은 서로 다른 상태다.

계정 상태가 작업 가능 여부보다 우선한다. 신규 배차 후보 선별·수락 시 `accountStatus=APPROVED`를 먼저 검증하고, 다음으로 `availability=READY`와 나머지 후보 조건을 확인한다. `READY`로 변경하는 것만으로 계정이 활성화되지는 않는다. 승인 대기·반려 기사의 안내·재신청 등 제한된 접근은 UC-08을 따른다.

#### 12. 위치정보 사용 가능 여부 상태 `driver.locationUsability`

**근거 문서와 내용**

[FR-05](../requirements/functional-requirements/fr-05-request-registration-and-dispatch-candidate-selection.md) 세부 10, [FR-06](../requirements/functional-requirements/fr-06-driver-gps-location-collection-and-management.md) 세부 4~7: 최신 위치와 마지막 갱신 시각을 관리하고, 오래된 위치를 최신 위치와 구분하며 유효하지 않은 위치를 거리 기반 배차 후보 선별에 사용하지 않는다.

**사용자 결정(2026-11-01)**

위치 존재 여부와 마지막 갱신 시각으로 `MISSING`(위치 없음) / `STALE`(유효시간 초과) / `VALID`(사용 가능)를 구분한다. 위치가 없으면 `MISSING`, 위치가 있고 마지막 갱신 이후 경과 시간이 유효시간을 초과하면 `STALE`, 유효시간 이내이면 `VALID`다. `MISSING`과 `STALE`은 거리 기반 후보 선별에 사용하지 않는다. 위치 유효시간의 구체적인 값은 기존과 같이 미결정이다.

**기존 내용에 덧붙여서 설계**

시간 경과만으로 `VALID → STALE`이 될 수 있으므로 조회·후보 선별 시 계산하는 값으로 표현할 수 있다. 새 위치를 수신하면 마지막 갱신 시각과 함께 다시 판단한다. 위치는 있으나 갱신 시각을 확인할 수 없는 데이터도 사용 가능하다고 판단하지 않는다. OS 권한 거부·수집 오류는 원인 정보로 별도 구분하며 이 상태만으로 권한 상태를 추정하지 않는다.

### 상태 예시와 처리 정책

| 대상 | 상태 예시 | 의미와 불변 조건 |
|---|---|---|
| 관리자 접수 검토 상태 `reception.reviewStatus` | `DRAFT`(검토 미확정) → `CONFIRMED`(검토 확정) | 확정 전 의뢰 생성 불가. AI 분석 완료와 관리자 검토 완료는 다름 |
| 접수 처리 단계 상태 | `recordingStatus`, `sttStatus`, `analysisStatus`: `PENDING`(실행 대기), `PROCESSING`(처리 중), `SUCCEEDED`(처리 성공), `FAILED`(처리 실패), `NOT_AVAILABLE`(자료 없음) | 단계별 실패와 자료 존재 여부 분리. 실패해도 수동 확정 가능 |
| 의뢰 상태 `request.status` | `OPEN`(진행 대상 의뢰) / `COMPLETED`(의뢰 완료) / `CANCELLED`(의뢰 취소) | 기사 취소 접수만으로 `CANCELLED`가 되지 않음. 현재 담당자의 최초 보고서 정상 제출 시 작업 `WORK_DONE`과 의뢰 `COMPLETED`를 함께 확정. 재방문·인계만으로 완료하지 않음 |
| 배차 회차 상태 `round.status` | `SEARCHING`(기사 후보 탐색 중) / `OFFERING`(배차 요청·응답 대기) / `ASSIGNED`(기사 배정 확정) / `NO_CANDIDATES`(탐색 종료·후보 없음) / `DELIVERY_FAILED`(전체 요청 전달 실패) / `NO_ACCEPT`(모든 기사 거절) / `ROUND_CLOSED`(만료 등 회차 종료) | 재배차마다 새 회차. 일부 전달 실패는 `OFFERING` 유지, 기사별 결과 기록 |
| 기사별 반응 상태 `offer.status` | `PENDING`(응답 대기) / `ACCEPTED`(수락) / `REJECTED`(거절) / `EXPIRED`(유효시간 만료) / `RESPONSE_CLOSED`(요청 마감) | 요청 대상 기사·회차·만료 시각 고정. 다른 기사 수락 시 나머지 요청 종료 |
| 전달 상태 `offer.deliveryStatus` | `PENDING`(전달 대기) / `PROVIDER_ACCEPTED`(전달 서비스 접수) / `FAILED`(전달 실패) | 실제 수신·확인은 별도 `receivedAt`, `viewedAt`. 확인 신호 없으면 null |
| 확정 배정 상태 `assignment.status` | `POSSIBLE`(유효 배정) / `RELEASED`(배정 해제) / `FINISHED`(배정 종료) | 의뢰별 현재 `POSSIBLE`은 최대 1개. `RELEASED`를 다시 POSSIBLE로 수정하지 않고 재배정 시 새 ID |
| 작업 상태 `work.status` | `NOT_STARTED`(시작 전) → `EN_ROUTE`(이동 중) → `ARRIVED`(현장 도착) → `IN_PROGRESS`(작업 중) → 보고서 제출 → `WORK_DONE`(작업 완료); `IN_PROGRESS` → `REVISIT_REQUIRED`(재방문 필요) → `EN_ROUTE` → `ARRIVED` → `IN_PROGRESS`; `TRANSFERRED`(인계 종료·설계 제안) | 같은 담당자는 같은 작업 유지. 담당자 변경 시 기존 작업 종료·새 작업 생성. 인계 종료는 완료 집계 제외 |
| 취소 후속 처리 상태 `cancellation.resolutionStatus` | `PENDING`(관리자 결정 대기) → `REDISPATCH`(재배차 결정) / `CANCEL_REQUEST`(의뢰 취소 결정) | 접수 시 이미 배정 해제. 두 종결 값 중 하나만 가능. `REDISPATCH`는 결정 완료이며 새 배정 완료를 뜻하지 않음 |
| 기사 작업 가능 여부 상태 `driver.availability` | `READY`(작업 가능·대기) / `VACANT`(작업 불가·휴식) | 계정이 `APPROVED`인 경우에만 배차 판단에 사용. 완료된 작업의 `POSSIBLE` 배정은 신규 수락 차단 사유가 아님 |
| 기사 계정 상태 `driver.accountStatus` | `PENDING_APPROVAL`(승인 대기) / `APPROVED`(활성) / `REJECTED`(반려) / `WITHDRAWN`(탈퇴) | 작업 가능 여부보다 우선. `APPROVED`가 아니면 `READY`여도 신규 배차 제외. 반려 후 검증·재신청 제출 시 승인 대기로 복귀 |
| 위치정보 사용 가능 여부 상태 `driver.locationUsability` | `MISSING`(위치 없음) / `STALE`(유효시간 초과) / `VALID`(사용 가능) | 위치 존재 여부·마지막 갱신 시각으로 판단. 거리 기반 후보 선별에는 `VALID`인 위치만 사용 |

취소 접수 시 기존 작업 진행값은 이력으로 보존하되 배정은 `RELEASED`가 된다. 응답의 `workStatus`만 보고 변경 권한을 판단하지 않는다. 재배차는 새 회차·기사별 요청·배정을 생성한다. **작업 완료는 최초 보고서의 정상 제출 성공 시점**이며, 작업 상태 변경 API에서 보고서 없이 `WORK_DONE`으로 바꾸지 않는다. 완료된 작업의 배정이 `POSSIBLE`로 남아 있어도 다른 적합한 의뢰를 수락할 수 있다. 기존 작업은 완료 상태를 유지하며, 배정이 유효하다는 이유로 다시 진행 중으로 바꾸지 않는다.

**보고서 설계 제안:** 최초 보고서 존재 여부와 `submittedAt`으로 미제출/제출을 구분하면 별도 보고서 상태 enum은 필수가 아니다. 임시 저장을 제공한다면 보고서 `DRAFT`(작성 중)/`SUBMITTED`(제출 완료)를 별도 관리하는 것이 적합하다. 이 보고서 상태와 임시 저장 제공 여부는 아직 제안이며 승인·반려 절차는 추가하지 않는다. 제출 가능 작업 상태는 `IN_PROGRESS + 본인 POSSIBLE 배정`을 제안하며, 보고서 저장과 작업 `WORK_DONE` 변경·완료 이벤트는 원자적으로 처리한다. 현장 작업을 마쳤지만 보고서 미제출인 동안은 아직 작업 완료가 아니므로 신규 수락 허용 여부는 별도 결정 사항이다.

초안 취소 허용 상태는 `NOT_STARTED`, `EN_ROUTE`, `ARRIVED`, `IN_PROGRESS`, `REVISIT_REQUIRED`이며 `WORK_DONE`, `TRANSFERRED`는 제외한다. 취소 허용 상태 목록은 설계 제안이다. 보고서 제출에 따른 의뢰 완료는 위 사용자 결정을 따르며, 배정 종료 시점과 인계받은 작업 완료 시 의뢰 전체 집계 기준은 후속 결정한다.

## BR-02 인증·권한·개인정보 접근

권한은 **인증 확인 → 계정 상태별 접근 범위 확인 → 요청 대상자·담당자 관계 확인 → 해당 동작의 상태 조건 확인** 순서로 판단한다. 기사 정상 기능은 `driver.accountStatus=APPROVED`가 선행 조건이다. `READY` 또는 `POSSIBLE`만으로 권한을 부여하지 않으며, 토큰에 남은 과거 권한만 신뢰하지 않고 요청 시점의 서버 최신 상태를 확인한다.

| 주체 | 허용 | 요청마다 확인할 사항 |
|---|---|---|
| 관리자 | 접수 검토·의뢰 등록·후속 처리·현황/이력 조회 | 인증/MFA 및 역할. 보고서 수정은 별도 `REPORT_EDIT` 권한 제안. 마스터/부 관리자 차등은 미확정 |
| 승인 대기 기사 `PENDING_APPROVAL` | 본인 승인 대기 상태 안내 등 제한된 접근 | 본인 계정과 상태 확인. 정상 배차·작업·채팅 등 주요 기능은 제한 |
| 반려 기사 `REJECTED` | 본인 반려 사유 확인·재신청·로그아웃 | 인증 후에도 정상 서비스 접근은 제한. 검증 후 재신청 제출 전까지 반려 상태 유지. UC-08의 제한된 접근만 허용 |
| 탈퇴 기사 `WITHDRAWN` | 정상 서비스 접근 불가 | 로그인 및 신규 배차 제한. 보존 자료의 관리자 조회는 별도 권한·보존 정책 적용 |
| 활성 기사 `APPROVED`·요청 대상자 | 본인 요청 조회 | 대상 기사 일치 및 조회 가능한 요청인지 확인. 마감·만료 안내와 응답 가능 여부를 구분하며, 조회에 신규 수락 조건을 일괄 적용하지 않음 |
| 활성 기사 `APPROVED`·요청 대상자 | 본인 유효 요청 수락 | `READY`, 대상 기사 일치, 요청 `PENDING`, 의뢰·회차 유효성, 만료 시각, 미완료 작업 점유와 나머지 후보 조건 재검증. `RESPONSE_CLOSED`, `EXPIRED`, `ROUND_CLOSED` 등 응답 불가 상태 확인 |
| 활성 기사 `APPROVED`·요청 대상자 | 본인 유효 요청 거절 | 대상 기사 일치 및 요청·회차·의뢰의 응답 가능 상태·만료 확인. 거절은 본인 요청만 종료하며 `READY`나 신규 작업 점유 가능 여부를 일괄 요구하지 않음 |
| 활성 기사 `APPROVED`·현재 담당자 | 작업 전이·취소 | 본인 `POSSIBLE` 배정과 현재 작업 상태에서 허용된 동작인지 확인. `WORK_DONE` 작업의 진행 재개·취소 또는 종료된 작업의 신규 변경은 허용하지 않음. 구체적인 취소 허용 상태는 BR-01의 초안 적용 |
| 활성 기사 `APPROVED`·현재 담당자 | 최초 보고서 제출 | 본인 `POSSIBLE` 배정·제출 허용 작업 상태·최초 보고서 존재 여부 확인. BR-01의 `IN_PROGRESS` 제출 조건은 제안이며, 정상 저장 성공 시 `WORK_DONE`으로 변경. 작업 변경 API로 완료를 직접 확정하지 않음 |
| 활성 기사 `APPROVED`·배정 해제 또는 작업 완료 기사 | 다른 적합한 배차 요청 수락 | 해제 후 관리자 결정 대기를 이유로 차단하지 않음. 완료된 `WORK_DONE` 작업의 `POSSIBLE` 배정도 신규 수락을 막지 않음. 계정 `APPROVED`·작업 가능 `READY` 및 나머지 수락 조건은 확인 |
| 활성 기사 `APPROVED`·재방문 인계받은 담당자 | 본인 새 작업 변경·연결된 이전 작업 기록 조회 | 새 작업의 본인 `POSSIBLE` 배정과 이전 작업 연결 관계 확인. 이전 기록은 조회 권한만 부여하고 이전 작업·보고서 수정 권한으로 확대하지 않음. 파일별 접근·보존 정책 적용 |
| 배정 해제·인계로 작업이 종료된 기존 담당자 | 이전 작업 신규 변경 불가 | 기존 작업 상태 변경·최초 보고서 신규 제출 차단. 새로 배정받은 다른 작업의 권한과 분리하며 과거 자료 조회 범위는 별도 개인정보 정책으로 확정 |
| 시스템 작업자 | STT/AI 처리, 후보 탐색, 요청/알림 전송 | 서비스 자격 증명·작업 ID 기반 중복 방지. 관리자/기사 공개 API와 분리 |

`POSSIBLE`은 배정이 유효하다는 뜻이며 모든 작업 동작을 허용한다는 뜻은 아니다. `WORK_DONE`이면 배정이 `POSSIBLE`로 남아 있어도 작업을 다시 진행하거나 최초 보고서를 새로 생성할 수 없다. 이미 정상 처리된 동일 요청의 재시도는 신규 변경과 구분하고 BR-03에 따라 현재 인증·조회 권한 확인 후 기존 처리 결과를 반환하거나 중복 안내한다. 보고서 최초 제출 이후의 정상 수정은 관리자 수정 권한과 BR-07을 따른다.

`READY`는 신규 배차 수락 조건이며 기존 배정의 작업 변경·보고서 제출까지 일괄 요구하지 않는다. `driver.locationUsability=VALID`는 거리 기반 후보 선별에 사용하는 위치 조건이다. 위치가 `MISSING` 또는 `STALE`이라는 이유만으로 이미 배정된 작업의 보고서 제출·관련 기록 조회를 차단하지 않는다. 각 동작의 계정·배정·작업·자료 접근 권한은 계속 검증한다.

녹음·사진은 비공개 저장소에 두고 파일 접근 API에서 역할·관련 의뢰 및 작업 관계·보존 정책을 확인한다. 재방문 인계로 이전 기록 조회를 허용해도 관련 없는 의뢰·작업·파일 접근 권한은 부여하지 않는다. 기사 탈퇴 후 보존/파기는 UC-15를 따르며 무기한 보존을 의미하지 않는다.

<a id="br-03"></a>

## BR-03 중복 요청·버전·오류 처리

- 인증 주체는 토큰에서 결정한다. 본문에 `driverId`, `adminId`, `releasedAt`, `updatedBy`를 받아 행위자로 신뢰하지 않는다. 시간은 시간대가 포함된 RFC 3339, 비용은 KRW 정수로 제안한다.
- 모든 대표 변경 API는 `Idempotency-Key` 필수. 키 범위는 `(인증 주체, HTTP method, 정규화한 경로, 키)`이며 본문 해시도 저장한다. 같은 키/본문 재시도는 최초 성공의 상태 코드와 본문을 재현하고 `Idempotency-Replayed: true`를 반환한다. 같은 키/다른 본문은 `409 IDEMPOTENCY_KEY_REUSED`. 처리 중이면 `409 OPERATION_IN_PROGRESS`와 `Retry-After`를 안내한다. 키 보존 기간은 미확정이며 앱의 오프라인 재시도 기간 이상으로 정한다.
- 키가 달라도 동일 업무가 중복되지 않도록 DB 제약을 둔다: 접수당 의뢰 하나(초안), 의뢰당 POSSIBLE 배정 하나, 배정당 취소 접수 하나, 취소당 후속 결정 하나, 작업당 최초 보고서 하나. 보고서 수정은 별도 revision ID로 누적한다. 재방문은 같은 담당자면 같은 작업, 담당자 변경 시 새 작업으로 구분한다.
- 중복 키의 기존 결과 반환은 현재 인증·조회 권한을 확인한 뒤 수행한다. 이미 해제/완료된 경우에도 같은 사용자의 정상 처리 재시도는 최초 성공으로 판별할 수 있어야 한다. 다른 키로 이미 처리된 업무를 재요청하면 `409`와 기존 리소스 ID·현재 상태를 반환한다.
- `expectedVersion`은 변경 대상 버전에 대한 낙관적 잠금이다. 의뢰/배정/취소/보고서 각각의 버전을 사용한다. 취소 후속 처리는 취소 버전 외에도 의뢰와 현재 회차/배정을 트랜잭션 안에서 재검증한다.
- 오류: `401` 인증 없음, `403` 권한 없음/배정 해제, `404` 조회 불가, `409` 상태·중복·동시성 충돌, `422` 입력 오류, `503` 일시 장애. 오류 본문은 `code`, `message`, `traceId`, `currentState`, `resourceId`, `fieldErrors`를 통일한다. 다른 기사 개인정보는 충돌 응답에도 노출하지 않는다.

## BR-04 접수 확정·의뢰 생성·배차 전달

- **사용자 결정(2026-11-01):** 접수 수정·저장은 `PATCH /receptions/{receptionId}`로 수행한다. 검토 확정 요청은 저장된 접수의 `expectedVersion`을 전달하고 서버는 해당 버전의 저장값을 검증하여 확정한다. 최종 입력값을 확정 요청에 중복 전송하지 않는다. 확정 후·의뢰 등록 후 수정 정책은 별도로 정한다.
- **요구사항 확정:** AI 원본과 관리자 최종 확정 데이터를 구분한다. 녹음·STT·AI 분석 실패 시에도 수동 입력을 통해 같은 검토 완료 절차를 진행한다. 존재하지 않는 원본 자료는 표시하지 않고 필수값 누락 시 확정을 제한한다.
- **구현 제안:** 접수 확정은 PATCH로 저장된 최종 데이터와 버전을 기준으로 검증한다. 희망 방문 종료 시각은 시작 이후여야 한다. 이미 확정한 접수를 다른 키로 재확정하면 충돌을 반환한다. 확정 후 수정 정책은 미결정이다.
- **요구사항 확정:** 의뢰는 관리자 검토가 완료된 접수에서 생성한다. 활성 계정·전문 분야·작업 가능 상태·활동 지역·유효 위치·현재 작업 여부에 따라 후보를 선별한다.
- **구현 제안:** 의뢰·최초 배차 회차·후보 탐색 outbox를 한 트랜잭션에 저장하고 후보 탐색과 전달은 비동기로 처리한다. 생성 성공 응답은 기사 수신 성공을 뜻하지 않는다. 접수당 의뢰 하나 제약은 초안 정책이다.
- **요구사항 확정:** 후보 없음·전체 전달 실패·일부 전달 실패를 구분한다. 일부 실패만으로 의뢰 전체를 실패 처리하지 않고 유효한 요청은 유지한다. 푸시 서비스 접수와 기사 실제 수신·확인을 구분한다.
- **사용자 결정(2026-11-01):** 배정 없이 종료된 회차의 의뢰는 관리자 후속 처리 대상으로 남고, 기존 의뢰에서 후속 배차를 시작할 수 있다. 후보 없음·전체 전달 실패·전체 거절·수락 없는 만료로 회차가 종료되어도 의뢰는 `OPEN`으로 유지한다. 후속 배차를 위해 새로운 고객 의뢰나 기사 취소 요청을 생성하지 않는다.
- **미결정:** 탐색 반경·확대·종료 조건·위치 유효시간·요청 만료·재시도 수치, 수동 배차의 직접 배정 여부, 등록 이후 접수 수정의 영향 범위.

<a id="br-05"></a>

## BR-05 동시 수락과 확정 배정

기사 A/B가 같은 의뢰의 서로 다른 요청을 수락하면 서버는 의뢰 행 잠금 또는 조건부 갱신과 POSSIBLE 배정 유일성 제약으로 한 명만 확정한다. 성공 트랜잭션에 요청 ACCEPTED·배정 생성·다른 요청 RESPONSE_CLOSED·상태 이벤트 outbox를 포함한다. 패자는 `409 OFFER_CLOSED`로 마감 화면(`2237:1440`)에 연결한다. 앱 버튼 비활성화만으로 경합을 막지 않는다. 기사 A가 서로 다른 두 의뢰를 동시에 수락하는 경합도 기사의 미완료 작업 점유에 대한 잠금/유일성으로 처리한다. 완료된 작업의 POSSIBLE 배정은 점유에서 제외한다.

수락 시 본인 요청인지와 활성 계정·작업 가능 상태·현재 미완료 작업 점유·유효 회차·만료 여부를 재검증한다. 거절은 해당 기사의 요청만 종료한다. 구체적인 잠금 방식은 구현 제안이며 한 의뢰에 한 명만 확정해야 한다는 조건은 요구사항이다.

<a id="br-06"></a>

## BR-06 작업 변경·취소 즉시 해제·후속 결정·이력

- **요구사항 확정:** 작업 상태 변경은 현재 유효한 담당자만 가능하며 허용된 전이인지 확인한다. 취소 정상 접수로 해제된 기사의 변경은 거부한다.
- **요구사항 확정:** 유효한 취소 요청 접수와 기존 배정 해제를 원자적으로 처리한다. 둘 중 일부만 반영되면 안 된다. 같은 배정에 대한 반복 요청은 취소·해제·관리자 후속 처리 요청을 중복 생성하지 않는다.
- **요구사항 확정:** 취소 접수 즉시 기사는 해제되고 다른 적합한 요청을 수락할 수 있다. 고객 의뢰는 유지되며 관리자가 재배차 또는 의뢰 취소 중 하나를 결정한다. 관리자 처리는 배정 해제 승인·반려가 아니다.
- **구현 제안:** 취소·배정 RELEASED·해제 이력·관리자 알림 outbox를 같은 트랜잭션에 저장한다. 취소와 작업 변경·보고서 제출은 같은 배정에 대해 직렬화한다. 취소 성공 응답은 해제 완료를 의미하므로 201을 제안한다. 알림 실패는 커밋된 해제를 되돌리지 않고 재시도한다.
- **요구사항 확정:** 관리자 결정은 최신 의뢰·배차·취소 처리 상태를 확인하고 하나만 원자적으로 확정한다. 두 관리자가 재배차와 의뢰 취소를 동시에 선택해도 한 결정만 성공한다.
- **구현 제안:** REDISPATCH는 결정·새 회차·탐색 outbox를 함께 저장한다. CANCEL_REQUEST는 결정과 고객 의뢰 종료를 함께 저장한다. 충돌 시 현재 처리 결과를 안내한다. 재배차 결정 후 후보가 없더라도 결정을 되돌리거나 같은 결정의 회차를 중복 생성하지 않는다.
- **사용자 결정(2026-11-01):** 배정 없이 종료된 회차의 의뢰는 관리자 후속 처리 대상으로 남고, 기존 의뢰에서 후속 배차를 시작할 수 있다. 최초 배차 실패뿐 아니라 `REDISPATCH` 결정 이후 배정 없이 종료된 경우에도 적용한다. 기존 취소 후속 결정을 다시 처리하지 않고, 의뢰의 최신 상태와 유효한 진행 회차·배정 유무를 확인한 뒤 별도의 후속 배차로 새 회차를 시작한다. 이전 회차와 결정 이력은 보존한다.
- **요구사항 확정:** 최초 배차부터 재배차까지 배정 기사·취소·해제 이력을 보존하고 현재 배정과 분리 조회한다. 과거 배정을 덮어쓰지 않는다.
- **미결정:** 취소 허용 작업 상태와 일반 완료 배정의 종료 시점, 인계 시점·이전 기록 조회 범위의 세부 계약. 작업 완료와 재방문 처리 정책은 BR-01의 사용자 결정을 따른다.

<a id="br-07"></a>

## BR-07 보고서 원본·수정 이력·집계

- **사용자 결정(2026-11-01):** 기사와 관리자 모두 단일 작업 비용 `totalCost`(KRW 정수)를 입력·조회·수정한다. 출장비·자재비·인건비로 분리하지 않으며 통계에도 최신 유효 작업 비용을 반영한다.
- **요구사항 확정:** 최초 제출 시점의 담당자·작업 상태·제출 권한을 확인한다. 취소·재배차로 권한을 잃은 기사는 제출할 수 없다. 동일 작업 최초 제출 반복으로 보고서·작업 이력·완료 집계가 중복되지 않아야 한다.
- **사용자 결정(2026-11-01):** 현재 유효한 담당자가 작업을 모두 마치고 최초 보고서를 정상 제출하면 작업은 `WORK_DONE`, 의뢰는 `COMPLETED`로 함께 변경한다. 보고서 미제출·저장 실패 시 둘 다 완료 처리하지 않는다. 관리자 보고서 수정은 이미 완료된 의뢰를 새로 완료 처리하지 않는다.
- **구현 제안:** 업로드된 전후 사진의 소유권·해당 작업 연결·업로드 완료를 검증한다. 최초 보고서·작업 WORK_DONE 변경·의뢰 COMPLETED 변경·이력/집계 이벤트를 함께 저장한다. 배정이 POSSIBLE로 남아 있어도 완료된 작업은 신규 수락을 막지 않는다. 배정 종료 시점은 후속 결정한다.
- **요구사항 확정:** 최초 제출 원본과 전후 사진을 보존한다. 관리자 수정은 항목·수정 전후 값·수정자·시각을 별도 이력으로 누적한다. 별도 승인·반려 없이 최신 유효 내용이 조회와 통계에 반영된다.
- **구현 제안:** 사진·원본·작성자 변경은 허용하지 않고 본문·진단·작업 비용만 수정한다. 수정 전후 값·행위자·시간은 서버에서 기록한다. 동시 수정은 보고서 버전으로 제어한다. 비용 외의 구체적인 수정 가능 항목은 팀 합의가 필요하다.
- **요구사항 확정:** 원본·수정 이력·첨부 파일의 접근과 보존·파기는 UC-15 정책을 따른다.

### 수정 및 집계 예시

관리자가 작업 비용을 105,000원으로 수정하는 요청·응답 예시는 [OpenAPI](openapi.yaml)의 `reviseWorkReport`를 참조한다. 최초 원본의 작업 비용 100,000원과 전후 사진은 유지하고, 수정 이력에 작업 비용 100,000→105,000 및 수정자·시각을 기록한다. `effective` 조회와 통계는 105,000원을 사용하되 완료 건수는 증가시키지 않는다. 수정과 통계 반영이 비동기라면 집계 버전/반영 시각을 노출하는 계약을 추가한다.

## BR-08 의뢰 현황·상세·기간 통계 조회

- **요구사항 확정:** 로그인한 관리자는 데이터 유무와 관계없이 하나의 의뢰 현황 및 통계 화면에 접근한다. 진행 중인 의뢰와 과거 완료·취소된 의뢰를 함께 조회하며, 조회 기간과 검색·필터 조건(상태·작업 유형·기사·지역)을 필요에 따라 조합한다. 상태는 BR-01의 의뢰·배차·작업 구분을 따른다.
- **요구사항 확정:** 설정한 조건의 의뢰 목록과 해당 조회 기간의 통계를 함께 제공한다. 기간 변경은 목록과 통계 조회에 함께 반영한다. 목록의 상태·작업 유형·기사·지역 필터를 통계에도 적용할지는 미결정이며, 같은 기간 사용과 별개로 확정해야 한다.
- **요구사항 확정:** 의뢰 상세에는 접수 정보·작업 유형·현재 배차 상태·배정 기사·최신 작업 진행 상태가 필요하다. 최초 배차부터 재배차까지의 배정 기사·취소·배정 해제 이력은 BR-06에 따라 현재 배차 상태와 구분한다. 최신 배차·작업 상태를 실시간 반영하되 전송 방식과 이벤트 계약은 후속 결정한다.
- **요구사항 확정:** 후보 미확보·전체 전달 실패는 정상 배차 진행과 구분한다. 일부 전달 실패는 기사별 전달 결과와 정상 전달된 기사에 대한 진행 상황을 함께 제공한다. 푸시 발행·전달 서비스 접수 성공을 실제 수신·확인 성공으로 표시하지 않는다(BR-04).
- **요구사항 확정:** 목록 결과 없음(UC-04 E2), 기간 통계 데이터 없음(E3), 선택한 의뢰 없음(E1), 목록·통계·상세 조회 실패(E4)를 구분해 안내할 수 있어야 한다. 조회는 기존 의뢰 데이터를 변경하지 않는다.
- **구현 제안:** 목록 결과 없음은 `200`과 빈 배열, 통계 데이터 없음은 `200`과 데이터 유무를 구분할 수 있는 응답, 의뢰 없음은 `404`로 표현한다. 데이터 없는 통계를 임의로 0으로 채우거나 조회 실패를 빈 결과로 바꾸지 않는다. 상세 이외의 응답 스키마와 조회 입력 계약은 후속 명세다.
- **요구사항 확정:** 보고서 기반 조회·통계는 BR-07의 최신 유효 수정 내용과 중복 방지 기준을 따른다. 기사 탈퇴 관련 조회·이력·통계 데이터에는 UC-15의 접근 통제와 보존·파기 정책을 적용한다.
- **미결정:** 필터 UI·API 구현 방식, 검색 대상·일치 방식, 지역 세부 분류, 통계 지표·계산 방식·집계 주기·집계 기준, 통계와 목록 필터의 연동 여부. 외부 형식 내보내기는 UC-04 A2의 선택 기능으로 정책 결정 후 명세한다.

## 미결정 사항

취소 허용 상태, 최초 보고서 제출 허용 작업 상태의 세부 조건, 배정 종료 시점, 보고서 임시 저장과 별도 상태 도입 여부, 현장 종료 후 보고서 미제출 중 신규 수락 여부, 인계 종료 상태명과 이전 기록 접근 범위, 거절·만료·전달 실패 혼합 회차의 종료 분류, 접수에서 여러 의뢰 분리 허용 여부, 등록 후 접수 수정 정책, 미배정 공개 작업 수락의 자격·노출 정책(FR-08에 존재하나 UC-10은 본인 요청 전제), 수동 배차의 직접 확정 허용 여부, 위치 유효시간/탐색·만료·재시도 수치, 멱등성 보존 기간, 통계 기간 기준 시각·필터 연동·수정 반영 지연, 관리자 세부 권한 및 개인정보 보존/파기 기간은 후속 결정 사항이다.

### 탐색 범위 확대의 의미

[UC-03](../requirements/use-cases/uc-03-dispatch-request.md) A2에 따라 초기 범위에서 적합한 기사 후보를 찾지 못했을 때 탐색 반경을 넓혀 다시 찾는 과정을 뜻한다. 예를 들어 3km에서 후보가 없으면 5km로 넓히는 식이며, 이 수치는 설명용이고 확정 정책이 아니다. 확대 중에는 `SEARCHING`을 유지하고, 종료 조건까지 후보가 없을 때 `NO_CANDIDATES`로 구분한다. 반경·탐색 차수는 상태값과 별도 정보로 표현할 수 있다.

## 핵심 검증 시나리오

아래는 구현 후 검증할 시나리오이며 현재 통과를 의미하지 않는다.

| 시나리오 | 기대 결과 |
|---|---|
| STT/AI 실패 후 수동 접수 확정 | 원본 존재 여부와 실패를 구분하고 유효한 필수값으로 확정 가능 |
| 두 기사가 같은 의뢰 동시 수락 | POSSIBLE 배정 1개, 패자는 마감 안내 |
| 한 기사가 서로 다른 의뢰 동시 수락 | 미완료 작업의 중복 점유 방지. 완료된 작업의 POSSIBLE 배정은 점유에서 제외 |
| 작업 완료 후 POSSIBLE 배정을 유지한 기사 수락 | READY 및 나머지 후보 조건을 만족하면 다른 의뢰 수락 가능 |
| 모든 기사 거절·회차 만료 | 전체 거절은 NO_ACCEPT, 수락 없이 만료된 회차는 ROUND_CLOSED |
| 재방문 담당자 유지·변경 | 유지 시 같은 작업에서 이동·도착 재진행. 변경 시 기존 작업 종료·새 작업 생성·이전 기록 연결 |
| 보고서 제출 성공·저장 실패 | 성공 시 보고서·작업 WORK_DONE·의뢰 COMPLETED를 함께 저장. 실패 시 작업 또는 의뢰 완료만 남기지 않음 |
| 배정 없이 회차 종료 후 관리자 후속 배차 | 기존 의뢰 OPEN 유지, 관리자 후속 처리 대상으로 표시. 새 의뢰·기사 취소 요청 없이 기존 의뢰에서 새 회차 시작 |
| 재배차 결정 후 후보 미확보와 후속 배차 | 기존 REDISPATCH 결정과 회차 이력 보존. 같은 취소 결정 재처리 없이 기존 의뢰에서 별도의 후속 배차 시작 |
| 취소 동일/다른 키 재시도 | 취소 1개·해제 1회·관리자 처리 1개 |
| 취소와 작업 변경/보고서 제출 경합 | 커밋 순서에 따른 일관된 결과, 해제 이후 신규 변경 차단 |
| 두 관리자의 재배차/의뢰 취소 경합 | 결정 1개, 재배차 결정당 새 회차 최대 1개 |
| 재배차 이후 이력 조회 | 현재 배정과 이전 회차의 기사·취소·해제 이력 분리 |
| 보고서 중복 제출·관리자 반복 저장 | 최초 보고서 1개, 유효 수정 이력 누적, 원본 사진 불변, 완료 건수 불변 |
| 후보 없음·전체/일부 전달 실패·푸시 접수 후 미확인 | 상태 구분, 일부 실패 시 유효 요청 유지, 확인되지 않은 수신을 성공으로 표시하지 않음 |
| 의뢰 현황 진입·기간 변경·조건 조합 | 데이터가 없어도 접근 가능, 진행 중·완료·취소 의뢰 조회, 변경한 기간의 목록·통계 함께 표시 |
| 목록 결과 없음·기간 통계 없음·선택 의뢰 없음·조회 장애 | 빈 목록·통계 데이터 없음·404·조회 오류 구분, 장애를 빈 결과로 표시하지 않음 |
| 의뢰 상세 조회·배차/작업 상태 변경 | 접수 정보·작업 유형·현재 배차·배정 기사·최신 작업 상태 표시, 과거 이력 분리, 조회에 의한 의뢰 데이터 변경 없음 |
| 보고서 수정·기사 탈퇴 후 현황/통계 조회 | 최신 유효 내용 반영, 완료 건수 중복 없음, UC-15 접근 통제·보존·파기 적용 |
