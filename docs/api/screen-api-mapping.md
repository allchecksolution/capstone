# 화면별 API 대응표

검토일: 2026-10-31. 상태: **설계 초안**. 대상은 **기사 앱 ver2와 관리자 앱**이며, 접수→의뢰 등록→배차→작업→취소·재배차 범위를 다룬다. 로그인·회원가입·프로필·채팅 등 전체 앱 기능을 모두 명세한 문서는 아니다.

이 표는 선택지 목록이 아니라 각 화면의 데이터·입력·버튼과 API를 연결한 목록이다. 여러 화면이 같은 API를 사용하면 [openapi.yaml](openapi.yaml)의 단일 계약을 재사용한다. 업무 조건은 [업무 규칙](business-rules.md), 문서 안내는 [README](README.md)를 참조한다.

- 경로 앞에는 `/api/v1`을 붙인다. 아래 URI도 제안이며 확정된 구현 경로가 아니다.
- **계약 초안**: OpenAPI에 요청·응답이 있으며 operationId를 표기했다.
- **후속 명세**: 화면에 필요하지만 아직 상세 계약을 작성하지 않았다.
- **정책 결정 후**: 선택 기능 또는 동작 정책부터 확정해야 한다.
- 화면 ID는 [Figma 파일](https://www.figma.com/design/PfyqT7huiwtz63yKpfJzmA/)의 node ID다. 여러 화면을 묶은 이전 표를 화면 단위로 분리했다. 오류·완료 화면은 원래 명령의 응답을 사용하며 화면마다 새 API를 만드는 것은 아니다.

실시간 변경 반영은 서버 최신 상태 조회를 기준으로 한다. 전송 방식과 이벤트 계약은 아직 미정이다. 대응표의 `me`는 인증된 기사이며 다른 기사를 지정하는 입력값이 아니다.

UC-04 조회는 기존 의뢰 데이터를 변경하지 않는다. 보고서 기반 조회·통계는 최신 유효 수정 내용 반영과 중복 방지 기준(BR-07)을, 기사 탈퇴 관련 데이터는 UC-15 정책을 따른다. 통계 지표·계산 방식·집계 주기·집계 기준은 미결정이며, 외부 형식 내보내기(UC-04 A2)는 선택 기능으로 정책 결정 후 명세한다.

### 추가로 정리해야 할 화면/요구사항 차이

- 구버전 기사 화면의 UC 번호가 다르다. 예: `UC-12 배차 요청 수락 및 거절`은 저장소 기준 UC-10이다. 명세 추적 기준은 저장소 UC와 ver2로 통일한다.
- 기사 보고서 입력(`2239:1168`)은 `작업 비용` 한 개, 관리자 앱 수정 화면(`2022:2634`)은 `자재비` 수정과 `합계` 자동 계산을 표시한다. 세부 비용의 최초 입력 방법을 맞춰야 한다. [OpenAPI 초안](openapi.yaml)의 출장비·자재비·인건비 분리 모델은 제안이며, 기사 입력 화면과 함께 확정해야 한다.
- 기사 배차 요청 상세(`2237:1342`)는 “정확한 주소는 수락 후 확인됩니다.”라고 안내한다. 기사별 요청 조회에는 지역·예상 거리만, 확정 배정 조회에는 권한 검증 후 상세 주소를 반환한다. 고객 연락처 공개 시점도 확정해야 한다.
- 현장 도착·이동 중은 화면에 있지만 FR-09·UC-11의 상세 상태는 미확정이다. 화면 라벨을 곧바로 확정 enum으로 간주하지 않는다.
- 임시 저장 화면(`2239:1239`)은 있으나 UC-12 A1은 선택 기능이다. MVP 포함 여부를 결정한 다음 별도 초안 API를 작성한다.
- 의뢰 등록 완료 화면(`2007:1271`)에 `접수 정보 수정` 버튼이 있다. 의뢰 등록 후 수정 허용 필드, 의뢰 스냅샷 갱신, 기존 요청 무효화·후보 재선정 여부는 요구사항에서 확정되지 않았다. 무조건 접수 PATCH를 호출하도록 연결하면 안 된다.
- 전달 실패·일부 실패·탐색 확대 개정 화면(`2254:6547`, `2254:6660`, `2294:1478`, `2294:1575`, `2294:1692`)은 UC-03·04의 예외를 구분한다. 푸시 서비스 접수와 기사 실제 수신·확인은 별도 데이터로 관리한다.
