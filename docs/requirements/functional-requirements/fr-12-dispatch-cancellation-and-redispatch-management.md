# FR-12 배차 취소 및 재배차 관리

기사의 작업 취소에는 일정 문제·장비 부족·이동 및 거리 문제·고객 연락 불가·기타 중 하나의 분류와 1~1,000자의 상세 사유를 모두 필수로 받는다. 공백뿐인 상세 사유는 허용하지 않고, 기타 이외의 분류에도 같은 기준을 적용한다. 입력 검증 실패 시 취소·배정 해제·알림을 처리하지 않으며, 코드와 보존 기준은 [BR-06](../../../apps/backend/docs/business-specification.md#br-06)을 따른다.

재배차 시 같은 의뢰에서 작업을 취소한 기사는 이후 후보에서 제외한다. 수락 전 거절·무응답·전달 실패만으로는 제외하지 않으며, 해당 기사는 다른 의뢰에서는 정상적으로 후보가 될 수 있다. 후보 선정과 수락 시 재검증 기준은 [BR-04](../../../apps/backend/docs/business-specification.md#br-04)를 따른다.

배차 회차의 담당 기사 미확보 또는 담당 기사의 작업 취소로 관리자 후속 처리가 필요해지면, 모든 권한 있는 관리자의 등록된 활성 기기에 푸시로 알린다. 정상 진행·완료는 조회 API로 확인하며, 알림 실패는 취소·배차 결과를 변경하지 않는다. 발행·전달 기준은 [BR-06](../../../apps/backend/docs/business-specification.md#br-06)을 따른다.

|---------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **요구사항 유형**   | 기사 / 관리자 / 시스템                                                                                                                                                                                                                                                     |
| **요구사항 명칭**   | 배차 취소 및 재배차 처리                                                                                                                                                                                                                                                     |
| **정의**        | 담당 기사가 작업 수행이 어려운 경우 배차 취소를 요청할 수 있으며 시스템과 관리자는 해당 의뢰의 후속 배차를 처리할 수 있어야 한다.                                                                                                                                                                                        |
| **세부 내용**     | 1. 담당 기사는 배차 취소를 요청할 수 있어야 한다.<br>2. 기사는 배차 취소 사유를 입력할 수 있어야 한다.<br>3. 시스템은 유효한 배정 여부와 취소 요청이 허용되는 상태인지 확인하고, 유효한 요청이면 취소 요청 접수와 기존 배정 해제를 원자적으로 처리해야 한다. 정상 접수 즉시 기사의 기존 배정은 종료되며, 취소 요청과 사유는 관리자 후속 처리를 기다리는 것으로 기록해야 한다. 취소 요청의 처리 상태와 의뢰 자체의 상태는 구분해야 한다.<br>4. 관리자에게 배차 취소 상황을 제공해야 한다.<br>5. 배정에서 해제된 기사는 해당 의뢰의 작업 상태를 변경할 수 없으며 다른 배차 요청을 수락할 수 있어야 한다. 배정 해제만으로 고객 의뢰 자체가 취소되지는 않아야 한다.<br>6. 관리자는 남아 있는 고객 의뢰에 대해 재배차 또는 의뢰 자체 취소를 결정할 수 있어야 한다. 시스템은 최신 의뢰 상태 및 배차 상태를 확인하고, 여러 관리자가 동시에 처리하더라도 두 결정 중 하나만 확정되도록 관리자 처리를 원자적으로 수행해야 한다. 이미 처리되었거나 다른 관리자가 처리 중인 요청은 중복 처리하지 않고, 중복·충돌 시 현재 처리 상태를 안내해야 한다.<br>7. 기존 배차 및 취소 이력을 보존해야 한다.<br>8. 시스템은 동시 요청에도 동일 배정의 취소 접수와 배정 해제가 한 번만 성공하도록 보장해야 한다. 이미 정상 처리된 요청은 취소 요청·관리자 후속 처리 요청을 중복 생성하거나 배정 해제를 반복하지 않고 기존 처리 결과를 반환하거나 중복 요청임을 안내해야 한다. |
| **설계 시 고려사항** | 과거 배차·취소 이력을 보존하고 현재 상태와 구분한다.<br>취소 허용 상태·원자적 전이는 [BR-01](../../../apps/backend/docs/business-specification.md#br-01), 재배차 후보 제외는 [BR-04](../../../apps/backend/docs/business-specification.md#br-04), 관리자 후속 결정·알림은 [BR-06](../../../apps/backend/docs/business-specification.md#br-06)을 따른다.<br>동시 처리·중복 방지 구현은 [Persistence Conventions](../../../apps/backend/docs/persistence-conventions.md)을 따른다. |
